Section 2.2

Which tier does a team start at?

This answers the team's second question: “we've settled the idea — shall we set up Docker and CI now, to be safe?”

Tier 1 — prototype

Weeks 1–2, when you still do not know what users need

  • something 5 people can look at within 48 hours
  • no server, no Docker, no CI
  • thrown away without regret

Tier 2 — the team's repo

Once there is a USP and ≥5 pieces of real feedback

  • built seriously, on the template
  • tests, CI, deployment all belong here
  • this is where the course lives

Both ways of getting it wrong

Too early: full Docker and CI in week 1, on an unvalidated idea → three weeks spent on infrastructure.

Too late: still hand-built prototype after the idea is settled → it breaks under load on demo day.

Crossing over

Carry exactly two things from tier 1 into tier 2: the real users' questions, and the validated USP. Not the code.

This is a question a mentor gets in week 1 of every cohort, and answering it with "it depends" is useless. Give the test: do you have a USP and five pieces of real feedback? No, then tier one. Yes, then tier two. Both failure modes are real and they look opposite. The infrastructure-first team feels productive for three weeks and has nothing to show a user. The prototype-forever team demos beautifully to one person and falls over at Demo Day. The crossing-over line is the part people miss. When you move up a tier, you carry the knowledge, not the code. Prototype code is meant to be thrown away, and a team that tries to "upgrade" it spends longer than a rewrite.

Section 3.1

The environment, and how to read an error message

A virtual environment is a private library box for this project — so other projects cannot break it, and it cannot break your machine.

Three commands, in this order

$ python3 -m venv .venv
$ source .venv/bin/activate
  # Windows: .venv\Scripts\activate
$ pip install -r requirements.txt

The two failures that cover almost everything

  • No module named … → installed, but the venv is not active
  • Permission denied on install → installing into the system Python; also no venv

Same fix for both: activate the venv, install again.

How to read an error

Find the ERROR line, or the last line of a Traceback block.

Ignore [notice] and WARNING.

“Just read the last line” — and where that advice breaks

That rule is only true for a Python Traceback. pip prints [notice] A new release of pip is available after the ERROR line — so the genuine last line is advice about upgrading pip, not the failure.

Exercise 2.1 walks straight into this. Do not warn them again.

Define a virtual environment in one sentence and move on; people do not need the full story today, they need to know why the command exists. Then the error-reading rule, which is the transferable half of this slide. Find the ERROR line, or the last line of a Traceback. Ignore notice and warning lines. Be honest about the correction in the red box, because the simpler advice is what everybody repeats. "Read the last line" is true for a Python traceback and false for pip, which prints its upgrade notice after the error. A mentor who tells a team to read the last line of a failed pip install is sending them to look at an irrelevant suggestion. Say where this came from: running the install, not writing the lesson. That is the argument for every facilitator doing the setup themselves before the session.

Section 4.1

Environment variables: never hardcode a key

This answers the team's third question: “I put the key in the config file, it's easier — is that a problem?”

The three rules

  • .env.example → committed, with placeholder values
  • .env → never, under any circumstance
  • .env and every .env.* variant are already in .gitignore
$ git check-ignore -v .env
.gitignore:16:.env	.env   # this must print something

If a key does reach GitHub

Revoke the key. Do not delete the commit.

Deleting the commit saves nothing: the key is already in the history, already on GitHub's servers, and already in anybody's clone.

This has happened here

A team in cohort 4 left a CI runner's credentials on a branch. The order of operations was: revoke the runner first, delete the branch second. Doing it the other way round leaves a live credential in every existing clone.

Three rules, and the one people get wrong is the third line of the red box. The instinct when a key leaks is to delete the commit, because it makes the visible evidence disappear. Say plainly why that fails: the commit is in the history, in GitHub's servers, in forks, and in every clone anybody already made. The only action that actually ends the exposure is revoking the key. The cohort-4 example is worth telling because the ordering is counter-intuitive and the room will remember it. Revoke first, clean up second. If you delete the branch first you have destroyed your own evidence and the credential is still live. Note also that a key in a repository is not only a security problem — it is a deliverable problem, because the team then cannot rotate it without breaking everybody's environment at once.

Section 4.2

A clean git status does not mean everything is committed

What .gitignore blocks appears nowhere — not in git status, not in git add ., not in your pull request.

What the template did

Its .gitignore ignored all of data/. Sensible for runtime data — a database, a cache.

But the project's own data lives there too. So rubric.yaml and the sample syllabi would never be committed, and git status would stay clean the whole time.

The facilitator fixed this when building the repo — data/ → data/* plus three exceptions. See DA-LUOC.md. The lesson stays.

The right check

$ git ls-files | grep data
data/rubric.yaml
data/plo.md
data/de-cuong/…

git status tells you about changes it is watching. git ls-files tells you what git actually has.

How a team meets this

“Why do I have that file and you don't?” — in week 3, with nobody able to explain it.

This slide is about a gap in a mental model, not about a command. People believe that a clean status means a clean repo, and for ignored files that is simply false. Walk the example: ignoring all of data slash is a reasonable decision for runtime data, and it silently excludes the project's own fixtures. Nothing warns you. The file is on your disk, your program reads it, your status is clean, and your teammate does not have it. Give them the distinction to remember: status reports on what git is watching; ls-files reports on what git has. When a team asks why a file is missing on one machine, ls-files is the first command, not status. The facilitator already fixed this in the team repo, and say so, because otherwise somebody will run the check in the lab and be confused that it passes.

Their main had not moved in three weeks while 21 other branches were busy. A mentor looking only at main would have concluded the team had stopped working.

Three branch names and one flow. Keep it short — the room will use it in the lab in twenty minutes. The cohort-4 story is the content of this slide. Section 6.1

Running the server, and the gift called Swagger UI

A clickable interface for trying an API — without writing a line of code. The single most useful tool for a mentor who does not code.

$ make run
# then open
http://localhost:8000/docs

# second terminal, server still running:
$ curl -s localhost:8000/health
{"status":"ok", …}

What to do with it

Pick an endpoint → Try it out → Execute. You have just called an API without writing code.

Session 08 uses this to call an endpoint as the wrong role and check that the server answers 403.

And the AI logging hook — deliverable #4

$ bash scripts/setup_hooks.sh
$ ls -a .git/hooks/ | grep pre-push

Hooks live in .git/, and .git/ is never committed — so every person runs this on their own machine. Somebody else running it does not help you.

Two rules about the hook

  • never call scripts/log_* by hand — it fabricates log entries
  • never bypass a failing hook with --no-verify — the push succeeds, the log does not, and you find out a week later
Do this live on the projector. Start the server, open the docs page, click Try it out on an endpoint, and let people see a request go out and a response come back. Then say why it matters to this room specifically: Swagger is a clickable interface to an API. A mentor who cannot read the code can still exercise every endpoint a team has built, which means they can check behaviour rather than take somebody's word for it. We come back to this in session 08 for permissions. The hook has one trap and it is organisational, not technical. Hooks live in the dot-git folder, which is never committed, so each person installs their own. Teams reliably assume someone installing it once covers everybody, and then four weeks of AI logs are missing from three machines. The no-verify warning deserves a sentence of its own. Bypassing the hook makes the error go away and silently stops the logging, and a missing deliverable is discovered far too late.

Section 7

Working with the agent — the rules are in the repo

These four lines live in CLAUDE.md, so the agent reads them itself. You do not have to repeat them every session.

① Cite the source

Which file, which section. “I read it somewhere in the repo” is not a citation.

② End with a check you run

The check is the part that is graded — not the code the agent produced. And do not let it run the check and report the result.

③ Do not decide for me

Scope, framework, thresholds, what to keep — those are yours. The agent proposes options.

④ Do not do the part that is the lesson

If today's exercise is reading an error message, the agent does not read it for you.

If the agent in this repo replies “which would you prefer?”, that is rule ③ working — not the agent being unhelpful.

Read all four aloud. They take a minute and they set the terms for the next thirteen sessions. Rule two is the one to press on. That is the session 01 failure mode wearing a different hat. Rule four explains something people find irritating at first. When an exercise is about reading an error, an agent that reads it for you has removed the exercise. The repo's rules say so, so the agent will push back, and the line at the bottom tells people that is working as intended.

Three lines of configuration move the tests from red to green — and it reaches the other machines through a pull request, not a chat message.

The closing exercise, and the one that ties the session together. Everybody runs the tests first, because a different result is a diagnosis of that person's environment, not of the repo. Catch those people here rather than letting them leave with a broken setup. Pair one works with the agent under the repo's rules: explain the cause in two sentences, propose the smallest fix, name the file, and stop for approval before editing. That sequence is the thing being practised, more than the pytest configuration itself. Pair two must not look at the fix first. Their job is to find the CI trap independently: open the Actions tab, see nothing, and work out why. The sentence to extract from them is that an absent green tick is not evidence of anything. Then they check it the only way available — check out the branch and run it. The closing line is the one to say slowly: a green CI is something you make, not something you are given. A team that accepts a template with red tests and leaves them red for six weeks ends up in week six unable to distinguish a new failure from an old one, and so nobody dares change anything.

Summary · Q&A · References

Six things to take away

1 · Setup is not a minor session

It decides whether week 4 deploys. “It works on my machine” starts here.

2 · Read the ERROR line

Not the last line. pip prints its notice after the error.

3 · Docs and code drift

In every project. The mentor is the person who compares them.

4 · Leaked key → revoke it

Deleting the commit saves nothing. Revoke first, clean up second.

5 · Clean status ≠ committed

git ls-files says what git has. git status only says what it is watching.

6 · Green CI is made, not given

And no green tick is not the same as red tests — check which branches the workflow watches.
