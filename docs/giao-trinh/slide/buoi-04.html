Why LangGraph: from a chain to a state machine

Chain (LangChain, linear pipeline)

A fixed sequence of steps: each step’s output is the next step’s input.

State machine (LangGraph, stateful graph)

Steps (nodes) joined by edges that can branch and loop, over a shared state.

AspectChain (LangChain)State machine (LangGraph)
Flow (control flow)Fixed A → B → C → DChosen at run time by edges and conditions
Branch and loopHard: no jumps, no going backReturn to an earlier step, jump on a condition
State (memory)Passed from step to step onlyKept across all steps, can be saved and resumed
Best forTranslate, summarise, extractMulti-step tasks with decisions and tools
Chapter 4 explains why the course uses LangGraph with one contrast: a chain versus a state machine. A chain — LangChain's basic idea — is a fixed sequence of steps: A, then B, then C, then D, where each step's output becomes the next step's input. That is ideal when the work always happens in the same order. The red dashed arrow shows what a chain cannot do: it cannot go back to an earlier step, it cannot branch, and it does not remember anything between steps beyond what is passed along. LangGraph is built on top of LangChain, but it models the application as a state machine. The steps are nodes, joined by edges. An edge can be conditional — the diamond — and an edge can point backwards, which creates a loop. All nodes read and write one shared state, the strip at the top. The table sums up the three abilities chapter 4 names: the agent can return to an earlier step, jump to a different step depending on a condition, and keep state across many steps. These are exactly the abilities an agent needs, and exactly what a chain lacks. Do not present this as "graphs are better". The last row matters: for translation or summarisation, a chain is simpler and therefore better. The next slide makes that rule explicit.

Section 1 · Agent

When should you use an agent?

Tip · the rule to remember from this chapter

Not every AI application needs an agent.

For a simple task — translating a text, summarising an article — a chain, or even one direct LLM call, is enough. An agent is needed only when:

1 · the task has multiple steps

2 · decisions are made at run time

3 · external tools are needed

Choose the simplest level that works

Example agent task: a research assistant that (1) analyses the question, (2) searches papers, (3) summarises each, (4) compares, (5) writes the report.

Five signals that a task needs an agent

  • Multi-step (sequential or parallel): several processing steps
  • Decision-making (choice): pick between different actions
  • Tool usage (external systems): APIs, databases, search
  • Feedback loop (iteration): one step’s result changes the next
  • Non-deterministic (open-ended): the path cannot be known in advance

None of the five? Use a chain. Only routing? See section 12.

This is the slide to slow down on. Chapter 4 marks it as a tip, and it is the most practical advice in the chapter: not every AI application needs an agent. Read the amber box aloud. If the task is simple — translate a text, summarise an article — a chain, or even a single direct LLM call, is enough. An agent becomes necessary only when three things are true: the task has several steps, decisions must be made while it runs, and it needs external tools. The figure on the left turns this into a spectrum. Moving right buys flexibility, but costs money, latency and predictability: more LLM calls, more paths to test, more ways to fail. The engineering habit is to choose the simplest level that works, and to move right only when a requirement forces you to. The right card is chapter 4's longer checklist of five signals: multi-step, decision-making, tool usage, a feedback loop where one result changes the next step, and a path that cannot be known in advance. The research assistant at the bottom left has all five, which is why it is the chapter's example of a perfect agent task. Mentor question for each team: which of the five signals does your project actually show? If the honest answer is none, the right architecture is a chain — and that is a good decision, not a lesser one. Section 12 returns to this with real team cases.

Anatomy of a LangGraph agent: state, nodes, edges

State (shared memory)

What the agent knows so far: one typed record that every node reads and updates.

Node (step, function)

What the agent does: one function, one job — call the LLM, a tool, or some logic.

Edge (transition)

What happens next:

direct · conditional · loop

Analogy: the state is a shared whiteboard, nodes are the workers, edges are the hand-off rules.

This is the general picture for the rest of the chapter. Every LangGraph agent, however large, is made of the same three things. The state, at the bottom, is the agent's shared memory: one typed record — here a query, search results, an answer and a counter. It is what the agent knows so far. The dotted lines show that every node reads it and writes back to it. Nodes are the boxes. Each node is one step, written as a function with one job: analyse the question, search, calculate, write the answer. Nodes are what the agent does. Edges are the arrows, and they decide what happens next. Grey arrows are direct edges: after analyze, always go to the router. The amber arrows leave the diamond: that is a conditional edge, and the label on each arrow is the value the routing function returns — "search", "calculate" or "answer". The dashed teal arrow is a loop: after searching, the agent can go back and analyse again. That cycle is the thing a chain cannot express. The analogy in the dark box is useful for non-programmers: the state is a whiteboard in the middle of the room, nodes are workers who read the whiteboard, do their job and write their result on it, and edges are the rules for who works next. Section 2 · State

State: the agent’s memory

Definition · state (agent memory, graph state)

The state is the agent’s working memory: one shared record that holds everything the agent knows during a run — messages, search results, drafts, counters. Every node reads it and returns updates to it.

Five properties

  • Shared (global): every node sees the same state
  • Typed (schema): each field has a name and a type
  • Partial updates (deltas): a node returns only what changed
  • Merge rules (reducers): overwrite or append each update
  • Persistent (checkpointed): can be saved after every step, then resumed

Can the state be a Python class? Yes — three options

class State(TypedDict):
    query: str

TypedDict · default; a plain dict with type hints, lightest

@dataclass
class State:
    query: str = ""

dataclass · adds default values

class State(BaseModel):
    query: str

Pydantic · validates values at run time; slower

Chapter 4 uses TypedDict: the class is the schema; at run time the state is still a dict.

The state during one run · “Giá vàng hôm nay?”

{ query }

— search →

{ query, search_results }

— answer →

Fields appear as nodes run.

Chapter 4 calls state the most important concept in LangGraph, so give it time. The high-level definition is in the dark box: the state is the agent's working memory — one shared record holding everything the agent knows during a run. Every node reads from it, and writes back to it when it finishes. The five properties are worth naming, because each one returns later. It is shared: every node sees the same record. It is typed: each field has a name and a type. Updates are partial: a node returns only the fields it changed. Merge rules, called reducers, decide whether an update overwrites a field or appends to it — that is the slide after next. And it can be persisted: a checkpointer can save it after every step, which section 12 uses for resuming sessions. A common question is whether the state can be a Python class. Yes. LangGraph accepts three ways to declare it: a TypedDict, which is the default and what chapter 4 uses; a dataclass, which adds default values; and a Pydantic model, which validates values at run time at some cost in speed. With TypedDict, the class is only a schema — at run time the state is still an ordinary dictionary. The strip at the bottom shows the state growing during one run of the gold-price question: at the start only the query exists; after the search node, search results appear; after the answer node, the answer appears. This is why fields must be allowed to be missing at the start — the topic of the next slide.

TypedDict: fields, optional fields, design rules

from typing import TypedDict, Annotated, Sequence
from langchain_core.messages import BaseMessage
from langgraph.graph.message import add_messages

class AgentState(TypedDict, total=False):
    """State for a research agent."""
    messages: Annotated[Sequence[BaseMessage], add_messages]
    query: str                 # the user's question
    search_results: list[str]  # filled by the search node
    draft: str                 # draft answer
    iteration: int             # loop counter

total=False (all fields optional)

Not every field exists from the first step. search_results stays absent until the search node has run, so nodes read with state.get("field", default).

Anatomy of a field (data slot)

A field is one named, typed slot in the state. Annotated attaches a merge rule.

Four design rules

  1. Store only what is needed — every node receives it
  2. Clear names: query, draft, not data1
  3. Exact types on every field
  4. Separate concerns: one state per kind of agent

Tip · YAGNI: start with the smallest state; add fields when a node needs them.

This is the declaration pattern from chapter 4. The state is a class that inherits from TypedDict. Each line inside is a field: a name, a type, and a comment saying who fills it. TypedDict acts as a schema — LangGraph reads it to know which fields exist and what type each one has. Look at the first field, messages. Its type is wrapped in Annotated, with add_messages as the second argument. The figure on the right takes that line apart: the field name, the type, and an optional reducer — a merge rule that says how new values combine with old ones. The next slide is entirely about reducers. The blue card explains total=False. It makes every field optional. That matters because the state grows during a run: search_results does not exist until the search node has finished. Nodes therefore read fields with state.get and a default value, instead of square brackets that would fail on a missing key. Close with chapter 4's four design rules: store only what the nodes need, because the whole state is passed to every node; use clear names; annotate exact types, which makes debugging easier; and keep separate states for different kinds of agents. The tip is YAGNI — you aren't gonna need it: start with the smallest state that works and add a field only when a node needs it. A TypedDict is easy to extend later.

    user_id: str
    conversation_id: str

Most common state bug

A list field without a reducer: every update silently overwrites the whole list. Use add_messages or operator.add.

A reducer is the merge rule for one field of the state. When a node returns a value, LangGraph does not simply store it: it asks the field's reducer how to combine the new value with the old one. There are two patterns. Overwrite is the default. A field declared without a reducer, such as query, is replaced completely: the old question disappears and the new one takes its place. That is right for single values — the query, the draft, a score or a counter. Accumulate is for lists. The messages field is annotated with add_messages, so when a node returns one new message, it is appended to the existing list instead of replacing it. Chapter 4 points out one subtle feature of add_messages: if a returned message has the same ID as one already in the list, it is updated in place rather than added again. That is useful when the model revises a previous message. The dark card is MessagesState, LangGraph's built-in state for the most common case, a chat-style agent. It contains exactly one field, messages, already wired to add_messages. You extend it by subclassing and adding your own fields, such as a user ID. The red card is chapter 4's warning, and the most common state bug in practice: a list field without a reducer. Every node that returns a list replaces the whole list, and earlier results vanish without any error. If you want accumulation, you must declare a reducer — add_messages for messages, or operator.add for a plain list.

Section 3 · Nodes

Nodes: the agent’s processing steps

Definition · node (step, processing unit)

A node is one step of the agent’s work: a Python function that receives the current state, does one job, and returns only the fields it changed.

1 · One job (single responsibility)

Analyse, search, or answer — never all three.

2 · Return changes (delta)

Read the whole state, return only updated fields.

3 · No mutation (pure function)

Never change the input state in place.

4 · Clear name (verb + object)

search_web, not process or step1.

✓ Correct: return only the changed field

def analyze_query(state: AgentState) -> dict:
    """Normalise the user's question."""
    query = state.get("query", "")
    return {"query": query.lower().strip()}

✗ Wrong: mutate the input, return everything

def bad_node(state: AgentState) -> dict:
    state["query"] = state["query"].lower()  # NO
    return state                     # whole state
The high-level definition is in the dark box: a node is one step of the agent's work. Technically it is an ordinary Python function. It receives the current state, does one job, and returns only the fields it changed. The figure on the right shows that contract. The node generate_answer receives a state that contains the query and the search results. It calls the LLM. It returns a small update — just the answer — and LangGraph merges that update into the state using the reducers from the previous section. The four cards are chapter 4's principles. One job per node, the single-responsibility rule. Return changes, not the whole state. Never mutate the input in place — chapter 4 says nodes should behave almost like pure functions. And name nodes with a verb and an object, such as analyze_query or search_web, never process, handle or step1. The two code blocks contrast the correct and the wrong version. The correct node reads the query with get and returns one key. The wrong node writes into the state it received and returns the whole thing. Why does this matter? Because returning everything overwrites fields other nodes may have updated, it bypasses the reducers, and it makes bugs very hard to trace. Chapter 4's key point: returning only the changed fields makes nodes easy to debug, easy to test and easy to understand.

Section 3 · Nodes

Sync and async nodes, and error handling

Sync (synchronous, blocking)

Each operation waits for the previous one.

Use: fast CPU work, parsing, rules.

Async (non-blocking)

While one call waits on I/O, others run.

Use: LLM, HTTP APIs, databases.

async def generate_answer(state: AgentState) -> dict:
    prompt = build_prompt(state["query"], state["search_results"])
    response = await llm.ainvoke(prompt)   # does not block
    return {"answer": response.content}

Error handling in a node (graceful failure)

Catch the exception, write the error into the state, and let an edge decide what happens next — never crash the graph.

async def search_web(state: AgentState) -> dict:
    try:
        results = await search_api(state.get("query", ""))
        return {"search_results": results}
    except ConnectionError:
        return {"search_results": [],
                "error": "Search API unreachable. Retry."}
    except Exception as e:
        return {"search_results": [],
                "error": f"Unknown error: {e}"}
Two practical questions about nodes: should a node be synchronous or asynchronous, and what should it do when something fails? Start with the definitions in the two small cards. A synchronous node does one operation at a time and waits for each to finish before starting the next. An asynchronous node can start a call, and while that call is waiting on the network, other work can run. The timeline makes the difference concrete: three calls that each take about a second take about three seconds in sequence, but about one second when their waiting overlaps. Chapter 4's rule is simple: use async whenever a node does I/O — calling an LLM, an HTTP API or a database. LangGraph supports both styles, but async is usually more efficient for agents that call many APIs. In code, the only differences are async def and await, and the LangChain method ainvoke instead of invoke. Plain CPU work such as parsing or simple rules can stay synchronous. On the right is error handling inside a node. The principle is graceful failure: catch the exception, return an error field in the state, and let the graph decide what to do. Notice the node returns an empty result list plus a human-readable error message. The small figure shows why: the next edge can read the error field and route to a retry, a dedicated error-handling node, or an answer based on whatever information is already there. Section 4 · Edges

Edges: how information flows between nodes

An edge (transition, connection) tells the graph which node runs next. If nodes are the stations, edges are the roads between them.

Directed edge (direct, fixed)

After node A finishes, node B always runs next.

graph.add_edge(START, "analyze")
graph.add_edge("search", "answer")
graph.add_edge("answer", END)

Conditional edge (branch, decision)

The next node is chosen at run time by a routing function.

graph.add_conditional_edges("analyze",
    route_after_analysis,            # function
    {"search": "search", "calculate": "calculate",
     "answer": "answer"})              # map

START, END (sentinels)

Special markers: every run begins at START and finishes at END.

Most real agents combine both kinds of edge.

Edges are the third building block. The high-level definition: an edge tells the graph which node runs next. Chapter 4's image: if nodes are the stations where work happens, edges are the roads between them. Read the figure left to right. The grey arrows are directed edges, also called direct or fixed edges: after START, always analyze; after analyze, always the routing step; after search or calculate, always answer; after answer, always END. There is no decision on a grey arrow. The amber arrows leave the diamond, and together they form one conditional edge. A routing function reads the state and returns a string — "search", "calculate" or "answer" — and that string selects the road. The labels on the amber arrows are exactly those return values. The three cards show the code. A directed edge is one call to add_edge with a source and a target. A conditional edge is one call to add_conditional_edges with three arguments: the source node, the routing function, and a map from each possible return value to a target node. START and END are sentinels — special markers LangGraph provides. Every run begins at START and finishes when it reaches END. Chapter 4's key point: edges are what turn a collection of nodes into an intelligent agent. Directed edges give a fixed flow, conditional edges give a flexible one, and most real agents use both. The next slide looks inside the diamond.

Section 4 · Edges

Routing functions: the decision inside a conditional edge

Definition · routing function (router, path function)

A function that reads the state and returns the name of the next node. It is the heart of a conditional edge.

Warning

The return value must be a key in the map; an unknown value raises an error. Always end with a default case.

Example 1 · route by the question (rule-based)

def route_after_analysis(state) -> str:
    q = state.get("query", "").lower()
    if "tính" in q or "bao nhiêu" in q:
        return "calculate"
    elif "tìm" in q or "search" in q:
        return "search"
    return "answer"              # default

Example 2 · continue or stop? (ReAct check)

def should_continue(state) -> str:
    last = state["messages"][-1]
    if getattr(last, "tool_calls", None):
        return "tools"               # run the tools
    return END                       # enough: stop

                            {"tools": "tools", END: END})

The routing function — usually a few lines of if, elif and else — returns a plain string, here "search". LangGraph looks that string up in the map given to add_conditional_edges, and runs the matching node. The red line in the map is chapter 4's warning: if the function returns a value that is not a key in the map, LangGraph raises an error. Section 6 · ReAct Pattern

ReAct: think, act, observe — then repeat

Definition · ReAct (Reasoning + Acting, tool-calling loop)

The agent pattern that alternates thinking and tool use: reason about what is needed, call a tool, read the result, and repeat until it can answer — the way people solve problems.

Practical example · one ReAct run

Question     “Giá vàng hôm nay bao nhiêu?”
Thought      I need today’s gold price → use search.
Action       search_web("giá vàng hôm nay")
Observation  SJC gold today: 78.5 million VND/tael
Thought      I have the information; I can answer.
Answer       SJC gold is 78.5 million VND per tael.

Use ReAct when

  • the answer needs several steps
  • the agent must decide if it needs more information
  • the path depends on intermediate results

Avoid ReAct when

  • one simple step → chain
  • a fixed flow, no decisions → workflow
  • maximum speed matters: each loop is another LLM call

Yao, S. et al. (2023). ReAct: Synergizing reasoning and acting in language models. ICLR.

ReAct — short for Reasoning plus Acting — is the most common way to build an agent, and chapter 4 calls it the foundation of most modern agents. High-level definition: the agent alternates thinking and tool use. It reasons about what it needs, calls a tool, reads the result, and repeats until it can answer. Chapter 4 compares it to how people solve problems: think, act, observe, repeat. Walk the loop in the figure. One: thought — the model looks at the question and the conversation so far and asks what it needs. Two: action — it calls a tool. Three: observation — the tool's result is added to the messages. Then back to thought. Only when the model judges that it has enough information does it take the exit to four, the answer. The LLM and the message history sit in the middle because every turn of the loop goes through them. The dark box on the right is chapter 4's worked example, the gold price question. One thought, one action, one observation, one more thought, and the answer. Harder questions simply go round the loop more times. The two cards are chapter 4's guidance on when to use it. Use ReAct when the answer needs several steps, when the agent must decide whether it needs more information, and when the path depends on intermediate results. Avoid it for a one-step task — use a chain — for a fixed flow without decisions — use a workflow — and when you need maximum speed, because every turn of the loop is another LLM call and adds latency and cost. Section 8 · RAG

RAG: answering from your own documents

RAG (Retrieval-Augmented Generation) finds the passages of your documents that are relevant to a question and gives them to the LLM, so it answers from your data instead of only from its training.

Chunk (passage)

A small piece of a document that can be retrieved alone.

Embedding (vector)

Numbers that capture meaning: similar texts get nearby vectors.

Vector store (vector DB)

Stores vectors and finds the nearest ones fast: Chroma, FAISS.

Similarity search (top-k)

Returns the k chunks closest in meaning to the question.

Key point: RAG solves “the LLM does not know your data” without fine-tuning — just put the relevant passages in the context. (Lewis et al., 2020)

RAG is the most common way to give an agent specialised knowledge. High-level definition in the dark box: retrieval-augmented generation finds the passages of your own documents that are relevant to a question, and gives them to the LLM, so the model answers from your data rather than only from what it learned in training. The figure has three phases, as in chapter 4. Phase one, index, happens offline and once. The documents are split into chunks, small pieces that can be retrieved on their own. Each chunk is passed through an embedding model, which turns text into a vector — a list of numbers that captures meaning. The vectors are saved in a vector store. This is rebuilt only when the documents change. Phase two, retrieve, happens for every question. The question is embedded with the same model, so it lands in the same space as the chunks. The vector store then performs a similarity search and returns the k nearest chunks — the passages closest in meaning to the question. Phase three, generate: the question and the retrieved chunks are put into one prompt, and the LLM writes an answer grounded in them, ideally with citations. The four cards define the vocabulary with synonyms. The last line is chapter 4's key point: RAG solves the problem that the LLM does not know your data, without fine-tuning, which is expensive and complicated. You only need to put the relevant documents into the context. The idea was introduced by Lewis and colleagues in 2020.

    assert result["query_type"] in ["factual", "analytical", "creative"]
    assert result["iteration"] == 0

Do not test with the real LLM: it varies run to run, costs money and is slow. Use it only for manual end-to-end checks or staging.

The last technical section is testing. The definition: an agent is non-deterministic — the same input can give a different output on each run — so you cannot test the whole agent the way you test an ordinary function. Chapter 4's answer is to test the deterministic parts: nodes and routing functions with a fixed state, and the whole graph with a mocked LLM, a fake model that returns scripted replies. The pyramid shows how many of each. At the bottom, many unit tests for nodes and routing functions: fast, cheap and stable. In the middle, fewer integration tests that run the whole graph with a mocked LLM, scripting one reply per LLM call — analyze, plan, synthesize, review. At the top, very few end-to-end tests with the real LLM, done manually or in a staging environment. On the right, two of chapter 4's tests. The first tests the routing function from section 7 with three cases: low score, so research again; high score, so finalize; low score but three iterations, so finalize anyway. It needs no LLM and no mock, which is why routing functions are the cheapest and most valuable thing to test — and that last case is exactly the loop exit from section 11. The second test patches the LLM call inside the analyze node so it returns a fixed JSON string, then checks the node's output: a valid query type and an iteration counter reset to zero. The red box is chapter 4's warning: do not test agents by calling the real LLM. With temperature above zero the output changes, it costs money, and it is slow. Mock the LLM in unit and integration tests. The routing-function test above is the one each team can write first for its own project.

Summary · Q&A · References

Fifteen ideas to take away

1

Agent decides its own path; use one only for multi-step, run-time decisions, tools.

2

State is typed shared memory; reducers overwrite or accumulate.

3

Nodes do one job and return only what changed; async for I/O.

4

Edges direct for fixed flow, conditional via a routing function.

5

Tools are described by name, docstring and type hints; never crash.

6

ReAct think → act → observe, until there is enough to answer.

7

Graph design state → nodes → linear edges → loop with a stop.

8

RAG grounds answers in your documents, without fine-tuning.

9

Harness the body around the model, kept in one place against drift.

10

MCP write a tool once as a server; every client can use it.

11

Loops stop in code: max iterations, budget, self-check, escape hatch.

12

Orchestration chain → router → graph → multi-agent: lowest step that fits.

13

Multi-LLM cheap model first; a judge different from the writer.

14

Errors three layers — tool, node, graph: fail gracefully.

15

Testing pyramid of tests with a mocked LLM; never test on the real one.
