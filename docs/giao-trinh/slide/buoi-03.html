Section 1 · 5-Block Architecture

Five blocks, one system — each with a specific role

This is chapter 3's three-tier picture (Front-End, Back-End, Agent) extended with the two supporting blocks the chapter only mentions in passing: Database and DevOps. The three top blocks process a request; the two lower blocks support them. Read the arrows as conversations, not one-way pipes. Each link has a request going right and a response coming back: input and view, an HTTP request and a JSON body or stream, task and result, prompt and tokens. That is why every arrow has two heads. The agent's model does not have to be a large hosted LLM. A tiny AI model — a small language model with roughly a few hundred million to a few billion parameters, such as the small Phi, Gemma, Qwen or Llama variants — can run locally for narrow tasks like classification, routing or extraction. LangGraph and LangChain orchestrate either kind of model in the same way. The LLM provider has a dashed border because it is not ours. It is an external service, paid per call, and it can be swapped — or replaced by a local tiny model where quality allows. The dashed box on the left adds two components real systems often need. A cache, such as Redis, keeps short-lived data close for fast reads. A queue, such as AWS SQS, holds long jobs — for example a syllabus review — so the Back-End can answer at once and a worker runs the job later. Both are stores, so they sit with block 4; the code that uses them lives in the Back-End. This chapter only names them — add them only when the project needs them, with the reason in an ADR.

Section 1 · 5-Block Architecture

The 5-block architecture as a real-world restaurant

The restaurant is for mentors who have never built software. Use it to remember each block's responsibility; the next slide translates it into technical terms. Walk one order through the picture using the numbered badges; the legend under the building gives one line per step. A guest orders from the menu (1). The waiter writes a ticket in a fixed format and carries it to the kitchen (2). The kitchen — the chef at the stove — checks the ticket and cooks by recipe (3). When an order needs something the recipes do not cover, the kitchen passes it to the R&D lab, which adjusts the dish to that specific order: it tries, tastes and refines until the result fits (4). Both the kitchen and the lab fetch ingredients from cold storage (5). The dish goes back through the waiter to the table (6). Two points deserve a pause. First, the R&D lab is not the kitchen: fixed procedures belong in the back-end; only requests that need adaptation belong in the agent. Teams often call an LLM for something a simple if-statement could do. Second, DevOps is not only renting the building once; it is keeping the restaurant open every day — inspections before opening (CI) and cameras and a logbook (monitoring). The guest never walks into the kitchen, and the R&D lab never serves tables: every order passes through the waiter.

Section 1 · 5-Block Architecture

Why five blocks? Three architectural properties

Property 1

Separation of concerns

Decomposing a system into distinct parts, each addressing a single concern, so that each part can be understood, developed and changed in isolation.

After Dijkstra (1974)

In practice: a UI fix never touches agent code; each block has its own tests and owner.

Restaurant: the chef does not take payments at the table.

Property 2

Scalability

The ability of a system to maintain acceptable performance as its load grows, by adding resources rather than redesigning.

After Kleppmann (2017)

In practice: scale each block independently. LLM inference is usually the bottleneck — add agent workers, not front-end servers.

Restaurant: more guests → more tables and waiters, not a second R&D lab.

Property 3

Technology flexibility

Blocks depend only on each other's interfaces, never on internal implementations, so one block can be replaced without changing the others.

Loose coupling · after Parnas (1972)

In practice: Streamlit → Next.js, OpenAI → Anthropic, SQLite → PostgreSQL — the API contract stays the same.

Restaurant: redecorating the room does not change the recipes.

These three properties are chapter 3's technical justification for splitting the system. Each card has a formal definition, its origin, what it looks like in a real project, and the restaurant version. Separation of concerns comes from Dijkstra's 1974 note "On the role of scientific thought". Scalability is defined here as in Kleppmann's "Designing Data-Intensive Applications": the question is not "is it fast" but "does it stay acceptable when load grows, and what do we add to keep it that way". Technology flexibility is the practical consequence of Parnas' 1972 information-hiding principle: hide each decision behind an interface. Connect scalability to the next sections: because the LLM call is slow, the back-end must not block while waiting. That is the reason for async/await in the FastAPI section.

Section 2 · Front-End

Common and widely used interface patterns for AI-aided projects: chat, dashboard

Chat interface

Purpose: conversational, turn-by-turn interaction in natural language.

Key elements: history, message list, streamed answer, sources, input box.

Best for: questions, assistance, exploration.

Dashboard

Purpose: aggregated, at-a-glance monitoring and decision support.

Key elements: KPI tiles, charts, tables, filters, status.

Best for: managers, reviewers, operations.

UI (user interface) = what users see: layout, colour, type, controls.   UX (user experience) = what users feel: speed, clarity, confidence.

The front-end is the face of the application: what users see and touch. For AI-aided projects it usually takes one of two common, widely used forms, often both in the same product. Chat is for people who ask: free text in, an answer out, with history on the left and sources under each answer. A dashboard is for people who watch: numbers, trends and status, aggregated from many conversations. The dark strip separates two words that are often mixed up. UI is how a button looks; UX is whether the user finds the button and trusts what happens when they press it. A beautiful interface where users get lost is good UI and bad UX.

Section 2 · Front-End

Front-end frameworks: React and Next.js

React · Meta, 2013

a.k.a. React.js, ReactJS · a UI library

A JavaScript library for building user interfaces: the screen is a tree of reusable components, and React keeps it in sync with the application's data.

Next.js · Vercel, 2016

a.k.a. NextJS · a React meta-framework

A web framework built on React for complete applications: it adds page routing, server-side rendering and server code.

Key terms

  • Library (toolkit): code you call when needed
  • Framework (app skeleton): structure that calls your code
  • Component (UI building block): reusable piece of UI
  • CSR (browser rendering): page built in the browser
  • SSR (server rendering): page built per request
  • SSG (pre-rendering): pages built once, at build time
  • Routing (navigation): which page answers which URL

Keep this at overview level. The two cards on the left give one high-level sentence each, and the Key terms box gives every technical word on the slide with a plainer synonym in italics. Mentors need three of them most: component, SSR and CSR. A component is a reusable piece of interface. SSR means the page is built on the server and sent ready-made — good for public pages and search engines. CSR means the browser builds the page with JavaScript — good for chat, which updates continuously without reloading. The table answers the common question "React or Next.js?". React is the engine; Next.js is the car built around it. If the team already has a separate back-end (for example FastAPI) and only needs an interactive app, React alone is enough. If the team needs public pages, SEO or wants server code next to the UI, Next.js adds that. The "Fit for AI agents" row is chapter 3's argument: streaming, flexibility and production readiness. The highlighted row is the main reason this course picks React: it scales. The same component model works for one chat widget and for a large product, the ecosystem and the pool of developers are the largest of any front-end library, and Meta runs it in production at very large scale. A team that starts with React does not have to rewrite the front-end when the project grows. Chapter 3 also notes that a Python prototype tool such as Streamlit or Gradio is a valid first step when time is short.

Section 2 · Front-End

Anatomy of a standard chat interface

1 · History — past sessions; start a new chat

2 · Header — assistant name, status, settings

3 · User message — right-aligned, role = "user"

4 · Assistant message — rendered Markdown: lists, tables, code

5 · Sources — each claim links to a document

6 · Message actions — copy, regenerate, rate the answer

7 · Streaming display — tokens appear as generated, with a typing indicator

8 · Input box — multi-line; Enter sends, Shift+Enter breaks a line; attach files

Data flow

Input box → POST /api/v1/chat → SSE stream → message list

Each message: { role, content, timestamp, sources }

SSE (Server-Sent Events): the browser opens one HTTP connection and keeps it open; the server pushes each new piece of text (token) as it is generated. One-way, server → browser — simpler than WebSockets.

This is chapter 3's chat design — input box, message list, streaming display — expanded to the eight elements users expect from a modern assistant. Walk the numbers. Elements 3, 4 and 8 are the minimum: a place to type and a list of messages with roles. Element 7, streaming, matters most for perceived speed: an agent can take 10 to 15 seconds, and a blank screen for that long feels broken. Element 5, sources, matters most for trust: an answer the user cannot check is an answer the user should not rely on. The dark box shows the wiring. The input box sends one HTTP request; the back-end answers with a Server-Sent Events stream; the front-end appends chunks to the last message. Every message is the same small object, which is also what the database will store.

Section 3 · Back-End

The back-end: the system's control centre

Definition

The back-end (server side, application server) is the part of an application that runs on the server: it receives requests, applies rules, coordinates data and services, and returns results. Clients see only its API.

Core responsibilities

  • API exposure (endpoints, routes): accept and validate requests
  • Authentication (authN, identity check): who is the caller? Failure → 401
  • Authorisation (authZ, access control): is the caller permitted? Failure → 403
  • Business logic (domain logic, services): rules and workflows
  • Orchestration (coordination): database, agent, external services
  • Error handling, logging (fault tolerance, observability): fail safely, record every event
Chapter 3 calls the back-end the "transit station": it receives requests from the front-end, handles all business logic that is not AI reasoning, calls the agent when needed, stores data, and returns results. Read the figure top to bottom as one request. It is routed and validated first — a malformed body stops here with 422. Then authentication asks who the caller is (401 if unknown) and authorisation asks whether that caller may do this (403 if not). Only then does business logic run, which may read or write the database and may call the agent. Finally a response is built: a JSON body or a stream. The two red-and-amber boxes at the bottom are cross-cutting: they wrap every step, not one. Error handling turns any failure into a safe message for the user and a detailed record for the team. Logging records every request so that problems can be traced afterwards. Stress the difference between 401 and 403. It is the most common confusion in student projects, and it is exactly where role-based rules live.

Definition

An ERD (data model) is a picture of what data a system stores and how it is connected — drawn before any table is built.

Section 5 · AI Agent

LangGraph: agents as stateful directed graphs

Definition

A LangGraph agent is a flowchart the program follows: it can branch, loop back and remember what happened so far.

Formally, a directed graph G = (V, E) over a shared state S:

  • Node (step): a function S → ΔS
  • Edge (transition): fixed, or conditional on S
  • State (shared memory): data every node reads and updates
  • Reducer (merge rule): how updates combine
  • Cycle (loop): repeat until END is reached

Common patterns built on the graph

  • ReAct (tool calling): reason → act → observe
  • Reflection (self-critique): review the draft, retry
  • Plan-and-execute: a planner, then workers
  • Persistence (checkpoints): resume, replay
  • Human-in-the-loop: approval before risky steps
  • Subgraphs (multi-agent): parallel teams
Start with the high-level sentence: a LangGraph agent is a flowchart the program follows, which can branch, loop and remember. Then the formal version, which chapter 3 states as a directed graph where each node is a processing step, each edge is a transition, and state is the data passed between nodes. Each term has a plainer synonym in italics: a node is a step, a function that takes the state and returns an update; an edge is a transition, fixed or decided by the state; reducers are merge rules; and cycles — loops — are allowed, which is what a simple chain cannot do. Walk the figure as one run. The LLM reasons and decides whether it needs a tool. If yes, the agent acts — calls search, a database or an API — observes the result by writing it into state, and loops back to reasoning. This loop is ReAct (Yao et al., 2023). If no tool is needed, the draft answer is evaluated. If it passes, the run ends; if not, it goes back for another attempt — the reflection pattern (Shinn et al., 2023). Every step reads and writes the same shared state, and the checkpointer can save it after each step. The list on the left names patterns teams will meet in tutorials and papers. Present them as vocabulary, not as requirements: most projects need only the first one, and some need none. A good mentor question is "which of these does your agent actually need, and why?".

Section 5 · AI Agent

Worked example: a routing agent, step by step

# 1 · STATE — the data every node shares
class AgentState(TypedDict):
    question: str
    context: Annotated[list[str], operator.add]  # reducer: append
    needs_search: bool
    answer: str

# 2 · NODES — each takes the state, returns an update
def router(state):                         # decide the path
    label = llm.invoke(f"Classify as simple|search: {state['question']}")
    return {"needs_search": "search" in label.content}

def search(state):                         # act: call a tool
    return {"context": [search_tool.invoke(state["question"])]}

def generate(state):                       # answer from context
    ctx = "\n".join(state["context"])
    return {"answer": llm.invoke(f"{ctx}\n\nQ: {state['question']}").content}

# 3 · EDGES — wire the nodes, then compile
g = StateGraph(AgentState)
g.add_node("router", router); g.add_node("search", search)
g.add_node("generate", generate); g.add_edge(START, "router")
g.add_conditional_edges("router",
    lambda s: "search" if s["needs_search"] else "generate")
g.add_edge("search", "generate"); g.add_edge("generate", END)
agent = g.compile()

Run A · “Xin chào!”

router → needs_search = False
generate → answers from the LLM alone
END · 2 nodes, 2 LLM calls, 0 tools

Run B · “Thời tiết Hà Nội hôm nay?”

router → needs_search = True
search → context = ["Hà Nội: 27°C…"]
generate → answer grounded in context
END · 3 nodes, 2 LLM calls, 1 tool

What to notice

  • Nodes return only what changed
  • operator.add appends to context
  • A conditional edge is a plain function
  • To loop, add an edge back to router, with a limit

Adapted from chapter 3. llm, search_tool and imports omitted.

This is chapter 3's example graph, shortened, with two traced runs. Read the code in its three labelled parts: state, nodes, edges. It is the same shape as the FastAPI file — declarations first, behaviour second, wiring last. Part 1, the state. It is a typed dictionary. The Annotated line is the only unusual part: it tells LangGraph that when a node returns new context, the new list should be added to the old one, not replace it. That is a reducer. Part 2, the nodes. Each one is an ordinary Python function: it receives the whole state and returns a small dictionary with only the keys it changed. The router asks the LLM to classify the question. The search node calls a tool. The generate node writes the answer using whatever context was collected. Part 3, the edges. START goes to the router. After the router, a conditional edge reads needs_search and chooses the next node. Search always goes to generate, and generate goes to END. compile() checks the graph and returns a runnable agent. Then walk the two runs on the right. A greeting skips the tool entirely. A weather question goes through search first. Same graph, different paths — decided at run time by the state. The last bullet shows how this becomes the loop from the previous slide: an edge from search or generate back to router, always with a maximum number of iterations so the agent cannot loop forever.

Section 6 · DevOps

DevOps: build, ship and run the system

Definition

DevOps (development + operations) is a set of practices, processes and tools that unify software development and IT operations, so changes are delivered quickly, safely and repeatably.

Core practices

  • CI (continuous integration): build and test every change
  • CD (continuous delivery): release tested changes automatically
  • Containers (Docker images): one package runs everywhere
  • IaC (infrastructure as code): servers defined in files
  • Observability (monitoring): logs, metrics, traces, alerts

DORA metrics (delivery performance): deployment frequency, lead time for changes, change failure rate, time to restore service

DevOps is the restaurant's licence, premises and daily operations: without it, the system lives only on a developer's laptop. Give the definition, then the loop: Dev on the left (plan, code, build, test), Ops on the right (release, deploy, operate, monitor), and the loop never stops because monitoring feeds the next plan. Every term on this slide has a plainer synonym in italics. The five practices are what teams actually set up. CI and CD in a pipeline such as GitHub Actions; Docker so that the same image runs on a laptop and on a server; infrastructure as code so the servers can be recreated; observability so problems are seen before users report them. The DORA metrics, from the Accelerate research, are the standard way to measure delivery performance. CD can also mean continuous deployment, where every passing change goes to production without a manual approval. Then walk the AWS figure as one request. A user's browser looks up the address in Route 53, the DNS service, reaches the load balancer, which forwards to one of the EC2 virtual servers in the auto scaling group. Each EC2 instance runs the same Docker image containing FastAPI and the agent. The servers read and write the managed PostgreSQL database in RDS and store files in S3; the agent calls an external LLM API. Logs and metrics go to CloudWatch. When code changes, GitHub Actions tests it, builds an image, pushes it to ECR, the container registry, and the servers pull the new image. Point out how the five blocks map onto the cloud: back-end and agent on EC2, database on RDS and S3, DevOps as everything that builds, deploys and watches them.

Definition · zoom levels (C4 model)

An architecture diagram (system diagram) is a map of a system: its parts, what each does, and how data flows between them — at one chosen level of detail.

C4 (Simon Brown): Context — system and users · Containers — apps, databases · Components — modules in one app · Code — classes.

Five rules (chapter 3)

  1. Clear names — never “Service A”
  2. Group with subgraphs (one box per block)
  3. Direction on every arrow; label data
  4. Number the steps of a sequential flow
  5. One idea per diagram

Summary · Q&A · References

Seven ideas to take away

1

Five blocks, each with one responsibility, connected by API contracts — the agent never faces users directly.

2

Front-end: chat for asking, dashboards for watching; judge it by correctness, speed, usability, accessibility.

3

Back-end: validate → authenticate → authorise → run logic → respond; async so the LLM never blocks the server.

4

Database: SQL for records (design with an ERD), vector stores for meaning; add only what you need.

5

Agent: a stateful directed graph — nodes, edges, state — that can branch and loop, unlike a chain.

6

DevOps: build, test, ship and watch every block automatically — containers, CI/CD, cloud, monitoring.

7

Diagrams are documentation: one question per picture, kept in Git, always matching the code.
