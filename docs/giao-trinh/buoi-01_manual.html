Phần 1Terminal: nơi bạn ra lệnh cho máy

Terminal là một cửa sổ bạn gõ chữ vào và máy làm. Không có nút bấm, không có menu. Đổi lại, mọi việc đều gọi tên được — nên đó cũng là ngôn ngữ duy nhất mà một agent có thể đưa cho bạn để bạn chạy lại y nguyên.

1.1 · Mở nó ra

macOS
Cmd + Space → gõ Terminal → Enter
Windows
Start → Git Bash (cài cùng Git). Đừng dùng Command Prompt cũ.
Trong VS Code
Ctrl + ` (dấu huyền, bên trái số 1)

1.2 · Đọc dòng nhắc lệnh

Dòng máy in ra trước khi bạn gõ gọi là prompt (dấu nhắc lệnh). Nó cho bạn biết bạn đang đứng ở đâu — và 90% lỗi của người mới là chạy lệnh đúng ở thư mục sai.

Prompt nói gì

an@MacBook-Pro mt-01-the-odyssey %
│  │                  │               └ hết prompt, phần bạn gõ bắt đầu ở đây
│  │                  └ thư mục bạn đang đứng  ← quan trọng nhất
│  └ tên máy
└ tên người dùng

Trong sổ tay này, mọi khối màu đen đều viết lệnh bằng màu vàng và kết quả máy in ra bằng màu xám. Bạn chỉ gõ phần màu vàng.

1.6 · Đọc lỗi — kỹ năng quan trọng nhất của buổi 01

Terminal không có hộp thoại báo lỗi. Nó in chữ, nhiều chữ, và dòng quan trọng thường không phải dòng cuối. Quy tắc đọc:

  1. Tìm dòng có chữ ERROR, hoặc dòng cuối của một khối Traceback.
  2. Bỏ qua mọi dòng bắt đầu bằng [notice] và WARNING. Chúng là lời nhắc, không phải lỗi.
  3. Đọc nguyên văn. Đừng đoán. Nếu không hiểu, copy đúng dòng đó đưa cho agent và hỏi.

Bẫy kinh điển — lỗi nằm ở giữa, không phải ở cuối

Phần 2GitHub: nơi mã nguồn của đội sống

Trước khi gõ lệnh nào, phải tách được hai thứ hay bị gộp làm một.

Nói gọn: Git là cái máy, GitHub là cái kho công cộng. Buổi 01 dùng cả hai, và mọi lệnh git … bạn gõ đều là Git — chỉ có push, pull, clone là thực sự nói chuyện với GitHub.

2.2 · Đọc một trang repo

TabBạn đến đây để

2.3 · HTTPS hay SSH

Nút Code xanh cho hai dạng đường link. Chọn một, và dùng nó suốt.

# HTTPS — dễ bắt đầu; GitHub sẽ hỏi tên đăng nhập và một Personal Access Token
https://github.com/UEH-ISB/mt-01-the-odyssey.git

# SSH — cài khoá một lần, sau đó không phải nhập gì nữa
git@github.com:UEH-ISB/mt-01-the-odyssey.git
Quan trọng

Khi GitHub hỏi mật khẩu trong terminal, nó không nhận mật khẩu đăng nhập website. Nó cần một Personal Access Token — tạo ở Settings → Developer settings → Personal access tokens. Token là mật khẩu: không dán vào file trong repo, không gửi trong chat nhóm.

  3. Mở tab Pull requests, ghi lại số PR đang mở.

  5. Vào docs/giao-trinh/ và mở 00-README.md ngay trên web.

Xong khi bạn nói được repo có mấy nhánh, mấy PR đang mở, và lần kiểm thử gần nhất kết quả thế nào.

Phần 4File Markdown và cách sửa bằng VS Code

Gần như toàn bộ tài liệu của The Odyssey là file .md. Lý do: đó là văn bản thuần, nên Git so sánh được từng dòng — và agent đọc được mà không cần mở ứng dụng nào.

4.1 · Markdown là gì

Markdown là quy ước dùng vài ký tự thường để ra định dạng. Bạn gõ **chữ**, khi hiển thị nó thành chữ. File vẫn là văn bản thuần — mở bằng cat cũng đọc được.

So với Word: Word nhúng định dạng vào một tệp nhị phân, nên Git chỉ biết “file đã đổi”. Markdown để Git chỉ đúng dòng nào đổi, chữ nào thêm vào. Đó là lý do cả bộ giáo trình nằm trong .md chứ không phải .docx.

Đường dẫn tương đối tính từ chỗ đặt file. Một liên kết viết trong docs/giao-trinh/slide/x.md trỏ tới file ở docs/giao-trinh/ phải là ../ten-file.md, không phải ten-file.md.

Phần 5Làm việc nhóm bằng Git

Phần dài nhất, và là phần duy nhất bạn sẽ lặp lại mỗi ngày. Học nó như học một vòng lặp tám bước, không phải học tám lệnh rời rạc.

1 · pull→ 2 · branch→ 3 · sửa→ 4 · add→ 5 · commit→ 6 · push→ 7 · PR + review→ 8 · merge↺

5.1 · Vì sao phải có nhánh

Cả bốn người cùng sửa main thì mỗi lần ai đó lưu, người khác lập tức bị ảnh hưởng — và không ai kịp đọc trước khi nó thành bản thật. Nhánh giải quyết điều đó: bạn sửa trong không gian riêng, xong rồi xin phép gộp vào.

Luật của đội

Không ai tự merge pull request của chính mình. PR của bạn phải có một người khác bấm Approve. Đây là luật, không phải lời khuyên.

5.2 · Bước 1–2 · Cập nhật rồi tách nhánh

git switch main          # chắc chắn đang đứng ở nhánh chính
git pull                 # lấy phần mới nhất của đội — LÀM TRƯỚC khi tách nhánh

git switch -c docs/an-sua-readme
Switched to a new branch 'docs/an-sua-readme'

git status
On branch docs/an-sua-readme
nothing to commit, working tree clean

-c là create: tạo nhánh mới rồi nhảy sang. Bỏ -c thì chỉ chuyển sang nhánh đã có.

Chữ thường, nối bằng dấu gạch ngang, không dấu tiếng Việt, không khoảng trắng. Tên nhánh hiện trong danh sách PR — người review đọc nó trước khi đọc mã.

5.3 · Bước 3–4 · Sửa, rồi chọn phần nào đem đi lưu

Giữa “đã sửa” và “đã commit” có một bước ở giữa, gọi là staging area (khu vực chờ). git add đưa thay đổi vào khu vực chờ; git commit mới thật sự lưu. Bước trung gian này để bạn commit đúng những gì liên quan, thay vì gom tất cả vào một cục.

git status — đọc ba vùng

Xem chính xác mình đã đổi gì, rồi mới add

Cẩn thận với git add .

Nó gom mọi file đang thay đổi, kể cả thứ bạn không có ý đẩy lên — file nháp, file khoá bí mật, thư mục tạm. Đọc git status trước, mỗi lần.

git status sạch không có nghĩa là đã lưu hết

git status chỉ so sánh với những file Git đang theo dõi. Một file bị .gitignore chặn, hay một file bạn chưa bao giờ git add, vẫn làm git status im lặng. Muốn biết thật sự repo đang giữ những gì, dùng:

git ls-files | wc -l              # repo đang theo dõi bao nhiêu file
git ls-files | grep giao-trinh    # file của tôi có nằm trong đó không
git status --ignored              # những gì đang bị .gitignore chặn

5.6 · Bước 7 · Mở pull request

  1. Mở đường link GitHub vừa in, hoặc vào tab Pull requests → New pull request.
  2. Kiểm tra hai hộp ở trên: base phải là main, compare là nhánh của bạn. Sai chiều là PR vô nghĩa.
  3. Tiêu đề: viết như lời nhắn commit — một câu, nói việc gì.
  4. Mô tả: ba dòng là đủ, theo mẫu dưới đây.
  5. Bên phải, ở Reviewers, chọn một người trong đội.
  6. Bấm Create pull request.

Mẫu mô tả PR — dán vào rồi điền

## Đã làm gì
Mô tả lại dòng buoi-02 trong bảng mục lục của 00-README.md.

## Vì sao
Dòng cũ chỉ ghi "Buổi 02", mentor mới không biết buổi đó dạy gì.

## Kiểm tra thế nào
Mở docs/giao-trinh/00-README.md trên tab Files changed, xem bảng hiện đúng.

5.7 · Review PR của người khác

Review là một nửa công việc, không phải việc phụ. Bạn sẽ review nhiều hơn là được review.

  1. Mở PR → tab Files changed. Màu xanh là dòng thêm, màu đỏ là dòng xoá.
  2. Đưa chuột vào một dòng, bấm dấu + xanh để góp ý đúng dòng đó.
  3. Bấm Review changes ở góc trên phải, chọn một trong ba:
Lựa chọnNghĩaDùng khi
CommentGóp ý, chưa kết luậnBạn có câu hỏi, chưa đồng ý cũng chưa phản đối
ApproveĐồng ý gộpBạn đã đọc hết và thấy đúng
Request changesYêu cầu sửa trước khi gộpCó chỗ sai, hoặc thiếu bằng chứng đã kiểm tra
Ba câu hỏi khi review

① Mô tả PR có nói rõ vì sao, không chỉ đã đổi gì?
② Có cách nào tôi tự kiểm tra lại được — một lệnh, một đường dẫn, một ảnh?
③ Có file nào bị kéo vào mà không liên quan đến việc này?

Góp ý nhận xét mã, không nhận xét người. “Dòng này nên dùng đường dẫn tương đối” — tốt. “Bạn làm cẩu thả” — vô ích.

5.8 · Bước 8 · Merge, rồi dọn dẹp

Người review bấm Merge pull request, không phải người viết. Sau khi PR được gộp, chủ nhánh về máy làm ba việc:

git switch main
git pull                                 # lấy về phần vừa được gộp
git branch -d docs/an-sua-readme         # xoá nhánh đã xong việc ở máy
Deleted branch docs/an-sua-readme (was 9a3f1c8).

Không xoá nhánh cũ thì sau ba tuần bạn có mười hai nhánh và không biết nhánh nào còn sống.

5.9 · Xung đột (conflict)

Xung đột xảy ra khi bạn và người khác sửa cùng một dòng của cùng một file. Git không tự đoán được ai đúng, nên nó dừng lại và hỏi bạn.

git pull
CONFLICT (content): Merge conflict in docs/giao-trinh/00-README.md
Automatic merge failed; fix conflicts and then commit the result.

Mở file đó bằng VS Code, bạn sẽ thấy dấu hiệu như sau:

<<<<<<< HEAD
| buoi-02.md | Buổi 02 — môi trường, Git, lỗi thật |     ← phần của BẠN
=======
| buoi-02.md | Buổi 02 — chuẩn bị môi trường |            ← phần của NGƯỜI KHÁC
>>>>>>> origin/main
  1. Quyết định giữ phần nào — hoặc viết lại một dòng gộp cả hai ý.
  2. Xoá sạch ba dòng dấu hiệu <<<<<<<, =======, >>>>>>>. Sót một dấu là file hỏng.
  3. Lưu, rồi git add <file> và git commit.
Cách ít gặp xung đột nhất

git pull trước khi tách nhánh, và giữ mỗi PR nhỏ. PR sửa một file thì gần như không bao giờ xung đột. PR sửa hai mươi file thì chắc chắn có.

Cả đội cùng sửa một bảng — sẽ có xung đột

Bài tập dưới đây cho cả bốn người điền vào cùng một bảng trong README.md. Ai merge sau gần như chắc chắn gặp CONFLICT. Đó là chủ ý: xung đột đầu tiên của bạn nên xảy ra ở một bảng đơn giản, lúc có người ngồi cạnh — không phải ở mã nguồn, lúc một mình. Cách gỡ ở mục 5.9.

Bài tập 5.1 · 20 phút · làm theo cặp

Một vòng lặp đầy đủ, từ nhánh đến merge

  1. Cả hai: git switch main rồi git pull.
  2. Cả hai: tách nhánh riêng, git switch -c docs/<tên-bạn>-tu-gioi-thieu.
  3. Cả hai: mở README.md ở gốc repo, tìm bảng Đội ngũ. Điền đúng một dòng của mình — tên, tài khoản GitHub, vai mình nhận trong đội, và câu mình chưa rõ về MT-01. Không sửa dòng của người khác.
  4. Cả hai: git diff để tự kiểm — chỉ được thấy một dòng đổi màu. Rồi git add README.md → git commit -m "docs: them <tên> vao bang Doi ngu" → git push -u origin <nhánh>.
  5. Cả hai: mở PR vào main, chọn người kia làm reviewer.
  6. Đổi vai: mỗi người mở PR của người kia, đọc tab Files changed, để lại một góp ý đúng dòng, rồi bấm Approve.
  7. Người review bấm Merge pull request. Không ai merge PR của mình.
  8. Cả hai: git switch main → git pull → git branch -d <nhánh>.
  9. Cả hai: git log --oneline -5. Phải thấy commit của cả hai người.

Xong khi bảng Đội ngũ trên main có dòng của cả hai người, mỗi PR có đúng một người khác Approve, và git branch ở máy không còn nhánh tạm nào.

6.6 · Ba việc không giao cho agent

Ranh giới

① Đừng để agent commit và push thay bạn khi bạn chưa đọc git diff. Tên bạn nằm trên commit đó. Người review sẽ hỏi bạn, không hỏi agent.

② Đừng dán khoá, token, mật khẩu vào khung chat. Cần khoá thì để nó trong .env — file đó đã bị .gitignore chặn sẵn.

③ Đừng tin agent khi nó nói về trạng thái repo. Nó hay nói chắc nịch những con số nó chưa hề đếm.

Agent đoán — và cách bắt quả tang trong 5 giây

Bài tập 6.1 · 12 phút

Bắt quả tang agent đoán — rồi bắt nó sửa cách trả lời

  1. cd vào repo đội, chạy claude.
  2. Hỏi nguyên văn: “repo này đang theo dõi bao nhiêu file?” — ghi lại câu trả lời.
  3. Thoát ra terminal, tự chạy git ls-files | wc -l. So hai con số.
  4. Vào lại bằng claude --resume, chọn đúng phiên vừa rồi. Yêu cầu: “từ giờ, mọi câu hỏi về trạng thái repo, hãy chạy lệnh trước rồi dán nguyên văn kết quả.”
  5. Hỏi lại cùng câu hỏi. Lần này nó phải chạy lệnh trước khi trả lời.
  6. Hỏi tiếp một câu có bẫy: “file docs/giao-trinh/buoi-05.md nói gì?” — file đó không tồn tại. Agent phải nói là không có, chứ không được bịa.

Xong khi bạn chỉ ra được một chỗ cụ thể agent nói sai về repo, và nối lại được phiên cũ bằng claude --resume thay vì mở phiên trắng.

Xoá commit không giải quyết được — khoá đã lộ từ giây nó lên mạng. Việc đúng là thu hồi khoá đó ở nơi phát hành và tạo khoá mới. File .env không bao giờ được commit; repo đã chặn sẵn mọi biến thể .env.* trong .gitignore, trừ .env.example.

Phần 11Việc về nhà và bảng tự kiểm

11.1 · Việc về nhà

Hiện vật phải nộp

Dòng của bạn trong bảng Đội ngũ của README.md, đã nằm trên main, qua một PR được người khác Approve và merge. Chỉ mở PR là chưa xong — PR còn đang mở nghĩa là chưa nộp.

  1. Hoàn tất dòng của bạn trong bảng Đội ngũ. Mở README.md ở gốc repo, điền đúng dòng của mình: tên, tài khoản GitHub, vai mình nhận trong đội, câu mình chưa rõ về MT-01. Làm trên một nhánh riêng, mở PR, nhờ một người trong đội review. Không sửa dòng của người khác, không sửa thẳng vào main.
  2. Review PR của một người khác trong đội: đọc tab Files changed, để lại ít nhất một góp ý đúng dòng, rồi Approve hoặc Request changes. Nhớ luật — không ai merge PR của chính mình, nên nếu bạn không review, PR của đồng đội nằm im.
  3. Ghi lại ba lỗi bạn đã gặp ở buổi 01 vào JOURNAL.md — vẫn qua PR, không sửa thẳng. Mỗi lỗi ba dòng: nguyên văn dòng máy in ra, nguyên nhân, và lệnh đã sửa được nó. Ghi vào file đã có sẵn, đừng tạo file mới.
  4. Chạy lại cả sáu bài tập trong sổ tay này một mình, không xem lại phần hướng dẫn. Mục tiêu: làm được vòng lặp tám bước mà không cần tra, và bắt được agent đoán ít nhất một lần.
  5. Viết ra giấy vòng lặp tám bước từ đầu đến cuối, không nhìn tài liệu, rồi đối chiếu với mục 5 của sổ tay này.
Nếu PR của bạn báo xung đột

Cả đội cùng sửa một bảng, nên ai merge sau sẽ gặp CONFLICT ở README.md. Giữ dòng của mình, giữ luôn dòng của người kia, xoá sạch ba dấu hiệu <<<<<<< / ======= / >>>>>>>, rồi commit. Chi tiết ở mục 5.9.
